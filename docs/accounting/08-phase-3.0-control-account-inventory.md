# Phase 3.0 — Control Account and Subledger Inventory

**Prepared:** 2026-11-15  
**Status:** Evidence-based implementation blueprint; Phase 3 is **not complete**.  
**Purpose:** Define the source populations, posting links, reconciliation feasibility, and remaining evidence needed before Phase 3.1 implementation.

## 1. Scope and evidence boundary

This is a static code/schema/documentation review. It does not assert that any balance is reconciled. No live or shared database was queried, no migration was applied, and no historical record was changed. Consequently, this report gives no record counts, balance amounts, verified opening balances, or confirmed historical exceptions. These must be computed in a positively identified isolated database and then tied to source evidence.

The primary implementation evidence is the chart and mappings in `backend/services/accountingPostingEngine.js`, models in `backend/prisma/schema.prisma`, the read-only `/api/accounting/subledger-reconciliation` implementation in `backend/controllers/accountingController.js`, and source-scoped calculators in `backend/services/*ReconciliationService.js`. The existing Admin and portal APIs initiate source transitions; accounting rules remain server-side.

### Feasibility meanings used here

- **READY:** Complete, independently evidenced source population and journal matching can be designed and run at the account level, including opening balance, period movement, cutoff, and exception handling.
- **PARTIAL:** A usable source/matching path exists for some events or current records, but completeness, external evidence, legacy/opening balances, or other source classes remain missing.
- **BLOCKED:** No reliable independent source population or approved calculation presently exists.
- **NOT_APPLICABLE:** The account is not a balance-sheet control account requiring a separate operational subledger. This does not exempt P&L source-to-journal testing or period review.

No material balance-sheet control is classified READY. The code’s `SOURCE_SCOPED`, `MATCH`, or displayed zero variance statuses only describe the records included in a given calculator; they do not upgrade this account-level feasibility assessment.

The account-level result is driven by source completeness and evidence, not by whether a comparator returns zero variance.

|---|---|---|

## 4. Historical exception inventory

### What is established from code

1. **Potential journal-without-source reference:** `JournalEntry.sourceType` and `sourceId` are plain nullable fields; no FK enforces that a source row exists. A `sourceType/sourceId` index is not unique. `idempotencyKey` is nullable and only prevents duplicates when callers supply the same non-null key.
2. **Potential source-without-journal:** historical `AccountPayable`, `AccountReceivable`, expenses, returns, cash transactions, fixed assets, loans and equity sources may exist without a matching posted journal. Some workflows have asynchronous/outbox or legacy posting behavior. The Accounting Event outbox is used for selected flows, not a universal source-event register.
3. **Duplicate postings:** unique journal idempotency keys protect only reused keys. Duplicate source pairs can still exist if older writers used different keys, omitted keys, or inconsistent source IDs. Global duplicate source scans are not implemented.
4. **Party identity:** `JournalLine.accountingPartyId`, `customerId`, and `supplierId` are nullable; legacy payable/receivable name/reference fields do not guarantee stable identities. Existing CPA and supplier-return comparators surface some identity/source issues for their scoped populations only.
5. **Unallocated amounts:** `AccountingDocument` tracks original/allocated/remaining values and `AccountingAllocation` has nullable idempotency and journal links. Open documents, credits, legacy payment histories and allocations without valid posted journals require a global exception scan. Some domain-specific checkers already validate those links.
6. **Dates/currency/amounts:** `JournalEntry` has transaction date but no currency column; `AccountingEvent.currency` is recorded as NPR in the posting engine. `AccountingDocument` has currency. Legacy source models still contain Float amounts (for example fixed assets, loans, shares, expense and distribution fields). Null, invalid, inconsistent currency and precision populations were not queried.
7. **Inventory historical limits:** cost-layer reconciliation intentionally excludes quantities without valid matching layers and flags damaged/in-transit/quarantine/return locations and lost stock. It does not infer a value from `Product.costPrice`; legacy or uncosted inventory remains an explicit exception.
8. **Gateway/bank/provider exceptions:** no payment-provider webhook or settlement ingestion was found in the repository search. NCM delivery webhooks are not gateway payment confirmations. 1180 has no provider-level independent subledger.
9. **Legacy/manual entries:** manual journals can legitimately lack an operational source. They must be separately categorized as approved manual entries, not silently counted as valid source-backed journals.

### Historical counts and balances not available in this review

No database rows were read. Therefore the following remain **unmeasured**, not zero: missing or duplicate source journals, orphan journal references, missing/duplicate party links, unsupported source types, open/unallocated credits/payments, null/invalid amounts or dates, non-NPR currency, and records outside reliable history.

P3.1 should produce read-only, cutoff-specific exception populations including:

- Posted source journals whose `sourceType/sourceId` has no source record, and source records in each in-scope domain with no expected posted journal or explicit pending/failed outbox event.
- Duplicate posted journals grouped by normalized source event identity and account effect, including same source with different idempotency keys; exclude approved linked reversals from duplicate counts.
- Required party missing, inactive/wrong party type, source ID mismatch, or party mismatch between journal lines, documents, allocations and source model.
- Document balance equation failures (`originalAmount != allocatedAmount + remainingAmount`), duplicate documents for one source, allocations without a posted journal, orphan journal IDs, and unallocated cash/credits past approved aging thresholds.
- Null or invalid source dates, journal transaction dates, currencies, debit/credit values, Float rounding conversion issues, and source dates crossing the chosen cutoff.
- Inventory balance/ledger/cost-layer mismatch, orphan layer movement, uncosted quantities, location-owner mismatch and quantity at sensitive locations.
- Treasury mapped to multiple ledgers or no GL, cash movements lacking source references, and bank/wallet statement lines not matched to system transactions.
- Tax return/assessment/payment/credit fields that do not tie to the associated filing journals and evidence.

These queries must be run sequentially against an isolated, positively identified database snapshot. Report each population, query version, cutoff, source evidence, hash, and disposition. Do not repair or backfill rows as part of exception discovery.

## 5. Account 1180 investigation

**Verified code facts:**

- The standard chart calls 1180 **Payment Gateway Clearing** and has a `PAYMENT_GATEWAY_CLEARING` mapping key.
- `treasuryAccountingService.js` permits 1180 as a Treasury asset and explicitly maps `WALLET` Treasury accounts to 1180; Treasury reconciliation sums all accounts by mapped GL account.
- The delivered-sale documentation and posting path use 1120 for non-COD tenders; 1180 is not the normal delivered-sale tender mapping.
- Other Treasury-based source flows can post to the GL code associated with the selected wallet, meaning wallet cash movements and any gateway-clearing entries share the same 1180 GL balance.
- Cash flow reporting intentionally includes 1180 as a cash equivalent and reports the aggregate GL amount. This is a presentation inclusion, not a wallet/provider reconciliation.
- Repository search found no provider payment webhook, provider settlement importer, provider transaction model, or provider-level gateway reconciliation; NCM carrier APIs/webhooks are a separate integration.

**Conclusion:** 1180 is a **combined and semantically ambiguous balance**. Its GL amount cannot currently be split reliably into company-controlled wallet cash versus payment-provider receivable/settlement-in-transit using the available account code alone. No amount or error is asserted.

**Minimum design before changing mappings:** agree the business meaning and historical handling; preserve the current historical GL; identify every `FinancialAccount` mapped to 1180; produce immutable by-account cash transaction and journal-source exports; obtain provider wallet and gateway statements with transaction, fee, refund and payout IDs; map new wallet activity separately from gateway receivables using explicit approved accounts or stable dimensions; then reconcile opening balance, activity, settlements-in-transit, fees/refunds and closing balance. Any reclassification must use authorized linked correction entries, not edits to posted journals. Until then, do not report all of 1180 as available bank cash or mark it reconciled.

## 6. Proposed implementation design for P3.1 onward

### Reuse before adding schema

- Keep `JournalEntry`/`JournalLine` as the GL evidence and `AccountingEvent` as the durable posting/outbox evidence for flows that use it.
- Use `AccountingDocument`, `AccountingParty`, and `AccountingAllocation` for invoice/bill balances, party identity, credit application and settlement matching.
- Use source-domain models (`FinancialAccount`, `CashTransaction`, inventory ledger/cost layers, tax filings, assets, settlement batches, loans, equity records) as independent operational schedules, with explicit limitations.
- Reuse and extend the pure source-scoped calculators already in `backend/services/`: Treasury GL, party subledger, NCM fee, fixed asset, inventory valuation, manufacturer production/logistics, customer refund, collaboration receivable and Marketing CPA.
- Reuse `/api/accounting/subledger-reconciliation` and the existing permission `accounting:subledger_read` for read-only inspection; reuse the period close checklist/pack and `AccountingPeriodCloseEvent.checklistSnapshot` for reviewed close evidence.
- Reuse the maker-checker approval and audit event models for review records; reconciliation must not write journals or silently clear exceptions.

### Smallest staged design

1. **P3.1 read-only account schedule:** extend the current reconciliation response through domain-specific query services. Each result must include account code/name/normal balance, cutoff and timezone, GL opening/debits/credits/closing, independent subledger calculation, source population counts, unmatched and invalid records, variance, coverage classification, source links, query/version and explicit limitations. Use Decimal-safe arithmetic; do not convert the whole account into one opaque UI total.
2. **Account-specific adapters, not one generic source table:** each domain supplies source rows and matching rules. Match on immutable source IDs, event type, party ID, document IDs, allocation/journal IDs, currency and dates. Never match financial events only by display name, invoice text or amount.
3. **Exception-only outputs:** retain matched rows and expose mismatches as exception records in the response. Empty source populations are not matches. Source-specific `MATCH` is subordinate to account-level coverage, which remains PARTIAL until all source families/openings are represented.
4. **Close evidence and approval:** freeze the cutoff, source population, GL snapshot, schedule, exceptions and deterministic content hash into the approved close pack; capture preparer and independent reviewer through existing period-close events. Reopen/recompute only through the existing controlled reopen lifecycle.
5. **No new DB model for initial P3.1:** current models and close snapshots can support the initial read-only blueprint and period review. If exception aging/disposition must persist independently of close snapshots, add a narrowly scoped `AccountingReconciliationRun` and child exception model only after data shape is proven. Such records should store the run/cutoff, account, source type/ID, journal/document IDs, exception code, measured values, evidence digest, status, owner and reviewer; never store editable copies of balances as accounting truth.
6. **Corrections stay in source workflows:** exception resolution is a linked source correction/reversal/approved journal action with audit attribution; the reconciliation run is read-only and does not create balancing entries.

### Proposed API boundary

- Keep `GET /api/accounting/subledger-reconciliation` read-only and permission-protected. Add validated `asOf`/period bounds only after consistent cutoff semantics are defined; default behavior must not imply a signed close.
- Add an account/source drill-down read endpoint only where the current response cannot explain an exception; expose stable source IDs, not sensitive evidence URLs unnecessarily.
- Persist an immutable snapshot only through the existing period-close submission/review flow (or a future reconciliation-run model if standalone retention/aging is required).
- No `POST reconcile`, auto-match mutation, balance adjustment, or journal posting API should be introduced under a reconciliation endpoint.

## 7. Recommended implementation order

1. **Lock scope and baseline:** identify the exact target database and cutoff; export the chart, current GL balances, journal roll-forwards, source populations, schema/migration versions and hash; no mutations.
2. **Cash/bank/1180:** inventory mappings and transaction families; distinguish physical cash, each bank, each wallet and gateway provider; capture independently sourced statements and unmatched items.
3. **1170/1190/2180/2185 COD and carrier:** finish source-document-to-batch-to-cash/fee/variance-to-allocation schedules, including the actual delivery-fee and payout evidence distinctions.
4. **2110/2160/2170/2190/2140 AP, party payables and refunds:** unify all open documents and legacy AP with journal lines, parties, payments and offsets; preserve distinct manufacturer/distributor/supplier workflow sources.
5. **1130/1150/1165/2120/2130 receivables and tax:** build filing-period and source evidence schedules; keep corporate tax/TDS blocked pending approved policies and assessment evidence.
6. **1140 and 5100 inventory/COGS:** reconcile source quantities and cost layers by location/ownership and cutoff, then trace sales/returns/transfer/damage effects. Do not price unresolved quantities.
7. **1510–1590, 2510, and 3100–3500:** fixed-asset, lender, and legal equity registers with external documents; resolve Float precision and opening records only through approved source corrections.
8. **P&L event completeness and close:** test every material revenue/cost/expense journal family and link the schedules to a period-close pack; keep estimates clearly separated.

At every stage, distinguish implemented, unit-tested, database-validated, source-evidence-verified, reconciled, management-approved, professionally reviewed, and production-approved. None substitutes for another.

## 9. Remaining risks and blockers

- No database-backed historical exception counts, balances, opening schedules or migrations were read or verified in this increment.
- No complete bank, cash-count, wallet, payment-gateway, lender, or legal share-register evidence ingestion/matching exists in the reviewed design.

- Opening balances, legacy source/journal relationships and source populations are not complete; journal source columns are not referential constraints.

- Money precision is inconsistent across the repository; several historical/operational models still use Float.
- Tax/VAT/TDS status and classification must remain evidence- and policy-gated; this report changes no treatment.
- Phase 3 is an implementation blueprint only. No account is marked reconciled, no journal adjustment is recommended or posted, and no Phase 3 completion is claimed.
