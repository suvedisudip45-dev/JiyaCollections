## 1. Scope and evidence boundary

This increment traces the code paths for customer receipts and reversals, NCM COD, distributor COD/remittances and balance settlements, returns/refunds/exchanges, manufacturer payouts, and Treasury movements. It distinguishes mounted production routes from service-only helpers and legacy handlers. It does not claim that any route was called in production or that a transaction persisted successfully.

No database, MySQL endpoint, production system, external payment provider, NCM service, bank account, or external accounting platform was accessed. No migration, seed, historical rewrite, or persisted validation was run. All described database transactions and balances are **VERIFIED_IN_CODE** only; transaction rollback, concurrency, migration state, actual records, and external cash receipt remain **NOT_VERIFIABLE_WITHOUT_DATABASE / INDEPENDENT EVIDENCE**.

Status labels used below:

- **VERIFIED_IN_CODE** — the current route/controller/service linkage and described code behavior are present.
- **PARTIAL** — a code path exists, but an evidence, source-population, lifecycle, policy, reader, or reversal link is incomplete.
- **MISSING** — no active end-to-end linkage was found for the stated transition.
- **LEGACY_OR_UNMOUNTED** — a legacy handler/helper exists but no active route/caller was found, or the route is explicitly disabled.
- **NOT_VERIFIABLE_WITHOUT_DATABASE** — static inspection cannot establish persisted state, deployment, actual population, rollback, concurrency, or external cash.

## 2. Bounded implementation slice

### Selected gap

The mounted invoice-receipt service already wrote a Decimal-valued NPR Treasury movement, customer-payment journal, invoice allocations, actor ID, and user-supplied evidence reference in one serializable transaction. It did not emit a receipt-specific `SystemAuditOutbox` event; the service's explicit audit write covered reversal only.

### Change

The canonical `POST /api/finance/collect-receivable` path now writes `CUSTOMER_RECEIPT_RECORDED` through the existing `recordSystemAudit` helper in the same service transaction, after journal posting and complete allocation. The audit event links the `CashTransaction` receipt ID to invoice IDs, accepted and settled amounts, adjustment type/amount, NPR currency, Treasury account, tender, journal ID, and allocation amounts. Authenticated actor, role, Admin portal, IP, user-agent, and correlation context are supplied by the controller. An audit-write error propagates rather than returning success; an unchanged idempotent replay does not add a second receipt audit event.

This adds no table, schema field, money calculation, route, or independent cash-verification claim. `SystemAuditOutbox` and its helper already exist in the codebase and are used by receipt reversal and other operations. Persistence of the new outbox row and rollback with the receipt remains unverified.

### Why other gaps were deferred

Direct-order actual receipt capture, a distributor remittance submission route, broad return/exchange corrections, and external bank/cash reconciliation do not meet the safe-slice criteria here. They need a stable source-event/tender contract, Phase 4 money/date coverage, route and population confirmation, or independent bank/physical receipt evidence. This iteration does not infer a cash receipt from `Order.payment`, a delivery status, a remittance declaration, uploaded evidence, or a balanced journal.

### Route and reader boundaries

- `financialRoute.js` imports `collectReceivable` from `treasuryAccountingController.js`. A similarly named exported handler remains in `financialController.js`, but it is not the mounted `/api/finance/collect-receivable` handler; do not infer production use from that legacy function.
- `orderController.cashReceived` is exported by the controller module but is absent from `orderRoute.js`; the existing `recordDeliveredOrderCashReceipt` helper and tests do not establish an active route.
- `submitDistributorRemittance` has service tests but no production controller/route caller. The Admin remittance review endpoint does not establish that a current distributor submission route exists.
- The NCM branch of the mounted finance collection handler normalizes its amount as an actual receipt, then passes it only as `expectedNetDeposit`; the NCM posting service requires `actualNetDeposit`. The separate delivery settlement-confirmation controller passes the actual amount field. The finance branch is not counted as a complete posting path.
- The receipt reconciliation endpoint checks internal receipt, invoice, allocation, Treasury, journal and reversal links. It explicitly does not consume bank statement lines or independently verified physical-cash evidence.
- The detailed posted-report basis and current report limitations are documented in [P5-R1](./19-p5-r1-accounting-domain-and-report-basis-inventory.md) and [R14's event/report matrix](./10-r14-accounting-event-matrix.md).

| Priority | Gap | Financial/control risk | Minimum safe prerequisite |

User-entered references, OTPs, uploaded images, distributor declarations and balanced journals are internal evidence only. | Receipt may be recorded without independent proof of funds; differences and duplicates against statements cannot be detected. | Separately approved source/evidence model and review procedure; independently authorized bank/cash evidence. |

| P1 | Posted distributor balance settlements and several return/exchange legs lack one universal source-linked correction/reversal flow. | Source, allocations, Treasury and GL may not all restore together after correction. | Define source and reversal semantics for each settlement/return leg; add focused failure/replay/reversal tests. |
| P2 | Return/exchange and some distributor settlement paths use legacy Number conversions or monetary source snapshots; receipt policy/reporting does not make all downstream amounts Decimal-backed. | R8/P4.2 semantic, rounding and source-precision issues remain; later catalog changes may not recover accepted historic values. | Complete R8 and P4.2 field and lifecycle coverage; preserve accepted snapshots and require separately authorized isolated validation. |

Two new mocked assertions verify receipt audit fields/replay behavior and that an audit-write error fails the request.
- `node --check` passed for `services/customerReceiptService.js`, `controllers/treasuryAccountingController.js`, and `tests/customerReceiptService.test.js`. `git diff --check` passed after the documentation updates. No backend lint script is defined; no portal build was relevant to this backend-only change.
