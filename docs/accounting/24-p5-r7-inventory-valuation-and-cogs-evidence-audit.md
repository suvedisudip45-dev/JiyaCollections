# P5-R7 — Inventory Valuation and COGS Evidence Audit

**Review date:** 2026-11-17
**Status:** **COMPLETE FOR THE DOCUMENTED STATIC INVENTORY, REPORT-BASIS, AND LABEL/DISCLOSURE SCOPE ONLY**
**Phase status:** Phase 5 remains **PARTIAL / INCOMPLETE**.

## 1. Scope and evidence boundary

This audit traced current inventory models, mounted production/order/return/transfer paths, cost sources, delivered-sale COGS posting, and first-party inventory/profitability readers. Repository evidence is authoritative for the code paths described here; no database rows, deployed configuration, physical inventory, ownership documents, supplier evidence, or posted balance was inspected.

No database connection or inspection, migration, seed, reset, historical rewrite, production/provider/bank access, or external supplier access was performed. No core order, fulfillment, inventory, return, settlement, or accounting-posting behavior was changed. The UI changes in this increment only disclose the verified source basis of existing amounts and quantities.

The audit rechecked the Phase 5 roadmap/tracker and P5-R1, P5-R2, P5-R4, P5-R5 and P5-R6 evidence; R8 and R24; and the R14 inventory/COGS, sales, return/exchange, and accounting-event documents. Relevant current-code paths include `schema.prisma`, inventory-ledger and production services, stock-transfer and order controllers, return/stock-return/exchange services, delivery/outbox/accounting services, and the mounted portal readers listed below.

### Evidence classifications

| Classification | Meaning |
|---|---|
| `VERIFIED_IN_CODE` | Static inspection confirms the current source path and its implementation (not deployed or persisted behavior). |
| `MOCKED_TESTED` | Existing tests exercise the path using mocks/in-memory state; they do not prove persisted correctness. |
| `PARTIAL` | The path or source population is incomplete, mixed with legacy behavior, or not fully traceable. |
| `MISSING` | No active, mounted end-to-end production path was found in the inspected code. |
| `NOT_VERIFIABLE_WITHOUT_DATABASE` | Requires persisted balances, events, or history to establish. Physical existence and legal title also require independent evidence. |

Cost classifications used below are `AUTHORITATIVE_COST_LAYER`, `HISTORICAL_COST_SNAPSHOT`, `REFERENCE_OR_CATALOG_COST`, `ESTIMATE`, `UNRECONCILED`, and `MISSING`.

## 2. Executive findings

1. The repository has a canonical, SKU/location-based quantity ledger, but it is not the exclusive writer or reader. `Product.stockQuantity` and variant JSON, `StockLog`, `ManufacturerInventory`, and `ManufacturerInventoryMovement` remain active in production paths.
2. The canonical inventory models record `inventoryOwner = PLATFORM`; manufacturer/distributor IDs identify a location or custodian, not a second owner class. The model cannot demonstrate supplier/manufacturer title or consignment status by itself. New production receipt code posts inventory and manufacturer payable together, consistent with the current production-completion rule, but legal title and older policy text still require reconciliation.
3. Production cost layers are the strongest available cost evidence, but only for their production request/SKU/variant scope. FIFO is used in selected allocation/consumption paths, not as one complete approved costing method across purchases, opening quantities, all returns, damage, and all legacy stock.
4. `Product.costPrice` is a mutable Float catalog field, not a cost layer. It is used as a fallback in delivered-sale COGS, operational analytics, and the Finance Dashboard's inventory-value estimate. Some resulting COGS or inventory amounts therefore lack a traceable receipt-cost layer.
5. Active return/exchange and direct-manufacturer paths can change `Product` or distributor/manufacturer stock without a matching canonical cost-layer-linked movement. Some of these paths also post or reverse inventory/COGS journals. The risk is confirmed in code; actual quantity/value discrepancies are not measurable without isolated persisted data.
6. No complete source-to-stock-to-layer-to-COGS-to-GL reconciliation is established. The Accounting Health inventory comparison is source-scoped and excludes unsupported/unmatched quantities; the operational Finance Dashboard uses a different, estimate-based formula.
7. No safe business-logic implementation meets the audit's evidence and policy gates. The bounded changes correct misleading portal labels and disclose the quantities/cost quotes' basis. The highest-risk return/legacy-stock correction is deferred pending ownership, return disposition, and cost-restoration policy.

## 3. Quantity source and ownership register

| Record/path | Quantity, variant, location, and ownership fields | Linkage and actual meaning |
|---|---|---|
| `InventorySku` / `InventoryBalance` | SKU is product + normalized size/color. `quantityOnHand` and `reservedQuantity` are whole-unit integers by location. | Canonical current on-hand/reserved balance. Available is generally `max(0, onHand - reserved)`. Reservations change availability, not total on-hand. |
| `InventoryLocation` / `InventoryLedgerEntry` | Location kind includes `FACTORY`, `DISTRIBUTOR`, `IN_TRANSIT`, `QUARANTINE`, `DAMAGED`, `LOST`, `RETURN_HOLD`, and `RETURN_RECEIPT`. Entry stores source/destination, integer quantity, movement type, reference, idempotency key, actor/reason, owner, and optional production cost-layer ID. | `applyInventoryMovement` updates balances and appends the movement in the caller's transaction; it checks source availability and exact idempotent replay. It does not require a cost layer for every movement. Current active paths enforce PLATFORM-owned locations/entries. |
| `Product.stockQuantity` / `Product.variants` | `stockQuantity` is an integer; variant quantities are JSON. It is not a universal stock balance. |
| `StockLog` | Product and optional variant labels, previous/new/change quantities, reason, order/source fields. | Legacy audit log, not an `InventoryLedgerEntry`; it is not consistently atomic with all legacy writes and does not record cost-layer or owner evidence. |
| `ManufacturerInventory` / `ManufacturerInventoryMovement` | Manufacturer/product, integer quantity and reservation, variant JSON, mutable proposed/agreed cost fields, price status. | Active manufacturer portal stock projection and legacy order/return path. | `ManufacturerInventoryCostLayer` / `ManufacturerInventoryCostAllocation` | Production request, manufacturer, product/SKU/variant, produced/available/reserved/consumed quantities, Decimal costs, and order/item allocations with returned quantity/state. | Production cost evidence and an allocation subledger. It is not itself a complete quantity ledger; counters can diverge from canonical balances or ledger movements. |
| Gift inventory | Separate gift assignment/stock events in `giftService`. | Promotional-gift availability is not garment inventory valuation or merchandise COGS; it is not included in the cost/valuation conclusions below. |

`inventoryOwner` is stored on canonical locations and ledger entries, defaults to `PLATFORM`, and the service rejects non-platform inventory ownership. A `FACTORY` location with `manufacturerId` is still recorded as PLATFORM-owned inventory in this model; the manufacturer ID denotes the location/custody association. Conversely, `ManufacturerInventory` does not prove that the units are legally manufacturer-owned. New production completion records good output in the canonical factory location and posts inventory/payable together. This does not verify physical existence or establish title from independent contract evidence.

## 4. Cost-source register and costing method

| Source | Classification | Current use and limitation |
|---|---|---|
| `ManufacturerInventoryCostLayer.unitCogs` (Decimal(30,14)), unit VAT/treatment, delivery cost (Decimal(20,2)), production request, variant, produced quantity | `AUTHORITATIVE_COST_LAYER` **for accepted production only** | Created from completed production actuals and accepted production cost terms. Layer IDs can flow to canonical receipt/transfer/fulfillment entries and order-item allocations. It is not a layer for purchases, every legacy Product unit, every return, or opening stock. |
| `ManufacturerInventoryCostAllocation` order/item/layer quantity and state | `HISTORICAL_COST_SNAPSHOT` / allocation evidence | Links selected manufacturer-order quantities to production layers; `returnedQuantity` and state capture part of return handling. | Accepted item `legacyUnitCogsVatInclusiveAtAcceptance`, agreed-unit-cost fields, and saved order-item JSON | `HISTORICAL_COST_SNAPSHOT` when populated from the accepted order; otherwise `UNRECONCILED` | Preserves a sale-time cost value for legacy quantities, but not a source layer or full receipt/issue lineage. | `Product.costPrice` (Float), item `costPrice`, `legacyInventoryUnitCogs` | `REFERENCE_OR_CATALOG_COST` | Mutable catalog field or copied compatibility snapshot. `postDeliveredOrderAccounting`, product analytics, and dashboard helpers use it for unlayered quantities; it is not an authoritative inventory cost layer. |
| `ManufacturerInventory.proposedCostPrice` / `agreedCostPrice` (Float) | `REFERENCE_OR_CATALOG_COST` | Manufacturer quote/approval and legacy direct-order input. Approval does not prove that the quoted amount was incurred for each currently held unit. |
| `InboundShipment.totalFreightCost`, customs/taxes, item/landed costs and paid/payable (Float/JSON) | `UNRECONCILED` | The schema stores acquisition-related numbers, but no active end-to-end purchase receipt to canonical balance plus cost-layer path was established. | Supplier-return `unitCostPrice` and `totalDebitCost` snapshot | `HISTORICAL_COST_SNAPSHOT` / `UNRECONCILED` | Request input is used for the supplier-return accounting amount; no direct original supplier receipt/layer association was found. |
| Cost for layerless distributor return/exchange, damaged/missing movement, or legacy opening stock | `MISSING` or `UNRECONCILED` | Quantities can be recorded without a linked cost layer. **Costing-method finding:** FIFO is implemented in selected production-layer allocation and distributor layer-consumption/return planning paths, with created-at/ID ordering in those paths. No single approved and fully implemented costing method was established for production, supplier purchases, landed costs, opening balances, all direct orders, damaged/lost stock, distributor returns, exchanges, and historic stock. Other reports use weighted production rates or Product cost fallbacks. Do not describe the system as using uniform FIFO or weighted-average inventory accounting.

## 5. Production COGS and accounting trace

| Order/source path | Fulfillment/movement and cost selection | Posting, retry, and evidence assessment |
|---|---|---|
| **Storefront order** | Order snapshot retains accepted selling price. Checkout also writes legacy Product stock; automatic assignment reserves PLATFORM-owned distributor balances. On distributor delivery, `consumeDistributorOrderInventory` issues quantity and attaches layer allocations where available. | `enqueueDeliveredSaleAccounting` stores a stable order-keyed payload/outbox event; `postDeliveredOrderAccounting` uses Decimal arithmetic for posted sale and COGS. An outbox failure can leave a committed inventory movement with COGS pending/failed/blocked; the status is visible, not evidence that the journal posted. Layerless quantities can use accepted legacy item cost or `Product.costPrice`. |
| **Admin direct order** | Order creation deducts Product stock/variants and writes `StockLog`, then allocates to a distributor. Canonical inventory is not consumed until the later fulfillment path. | No direct COGS posting at the Admin order-creation stock decrement. A delivered order follows the delivery/outbox path. Order/item cost source for layerless units remains a snapshot/fallback, not proof of receipt cost. |
| **Manufacturer direct order** | Mounted as a distinct direct-order workflow. It reserves/consumes production allocations and uses accepted item/layer costs. It does not create a canonical factory fulfillment movement; its legacy inventory decrement is after the order/accounting transaction. | Walk-in posting occurs within the order transaction, but canonical balance and that posting are not linked by a factory issue movement. Non-walk-in fulfillment and the legacy projection remain separate. This path is not a storefront manufacturer allocation and is not treated as proof that all manufacturer stock is platform-owned. |
| **Distributor direct order** | `consumeDistributorOrderInventory` writes order-referenced canonical `FULFILLMENT` movements. It uses linked production layers when available and preserves `legacyCostQuantity` for the uncovered amount. | Walk-in sale posts synchronously in the transaction; other delivered direct sales use the delivered-sale path. For unlayered quantities `postDeliveredOrderAccounting` accepts `legacyInventoryUnitCogs ?? item.costPrice`; missing/zero cost can leave the movement uncosted or produce no supported COGS amount. The `Product.costPrice` fallback is not an authoritative layer. |
| **Manufacturer assignment branch** | `/api/assignment/accept/:id` remains authorized for manufacturer assignment contexts, and `acceptOrder` retains a branch using `ManufacturerInventoryCostAllocation`/production layers. | The current automatic allocator selects distributors and canonical distributor stock; normal checkout does not establish a manufacturer assignment. Legacy assignment records and their fulfillment/stock linkage were not database-verified. |
| **Partial fulfillment, split delivery, multi-item orders** | The delivered-sale poster validates item quantity against production allocations plus `legacyCostQuantity` when allocations are present. Distributor consumption expects each item/SKU quantity to match the recorded fulfillment movement. | This is not proof of a universal partial-delivery cost schedule across every split/direct/legacy route. No generalized per-delivery partial COGS and reconciliation contract was established. **PARTIAL.** |
| **Cancellation before handoff** | Reservation/allocation is released; no delivered-sale COGS should be posted. | The cancellation service uses the separate release path and does not treat an order cancellation as a sale reversal. Post-handoff cancellation requires return/RTO evidence. **VERIFIED_IN_CODE.** |
| **Customer return / refund / exchange** | Customer restock can update legacy Product/ManufacturerInventory without a canonical return movement. For manufacturer-linked returns, the workflow restores available layer quantity only for matching consumed allocations and computes `restockedInventoryCost` from those layer costs. It does not require all returned quantity to be covered by allocations before increasing the legacy quantity. Damaged return cost uses saved `unitCostPrice`. Distributor self-delivery/exchange returns can add canonical stock without a cost-layer ID. | Non-distributor customer returns can post an RMA journal: linked restock cost debits 1140/credits 5100; damaged cost debits scrap loss 5500/credits 5100. These costs are accumulated with JavaScript `Number` in the workflow/poster. The RMA journal is not paired with a canonical return/damage movement. Distributor return accounting is a separate path. A complete matched reversal of original movement, cost layer, COGS, inventory asset, refund, and return location is not established. |
| **Supplier purchase/return** | Inbound shipment has cost fields but no active canonical receipt/layer caller was found. Supplier return reduces legacy Product stock and snapshots user-provided unit cost. | Supplier-return accounting may credit inventory without a matching canonical quantity/layer issue. No complete purchase-to-receipt-to-layer-to-AP-to-return reversal path was established. |

`postDeliveredOrderAccounting` uses shared Decimal helpers and checks item/production allocation quantities on the covered path. That is a valuable code-level control, but a balanced journal cannot prove that the source stock existed, that the selected cost was incurred, or that the canonical issue movement is complete. A delivered-sale event and its COGS journal can also be in different transactions because outbox processing follows the committed delivery/inventory transaction.

## 7. Evidence-backed mismatch and risk matrix

| Finding | Evidence/status | Consequence and boundary |
|---|---|---|

Canonical movement helpers and delivered-sale accounting events use unique idempotency keys and detect exact/conflicting replays in code. ### Highest-risk gap and next bounded implementation

The highest-risk confirmed gap is the **return/exchange-to-inventory-to-COGS link**: accepted goods can be restored to legacy or canonical quantity without restoring the same cost layer and original issue reference; meanwhile the return journal may reverse 1140/5100 from only a subset/snapshot of the returned quantity. A safe correction must first establish:

1. Owner and destination location for each return route (platform, manufacturer custody, distributor custody, quarantine, damaged, or lost).
2. The original order item, canonical fulfillment movement, and exact cost-layer allocation for every returned unit, including layerless legacy units.
3. Approved inspection/disposition and whether cost is restored to the original layer, a new return layer, or written off.
4. A single atomic/idempotent operation tying accepted physical receipt, quantity movement, layer counters, refund/credit, and journal reversal together.
5. Treatment of supplier receipts, customer returns, exchanges, distributor self-delivery returns, and historical stock separately; no assumed conversion of `Product.costPrice` to a layer.

This increment defers that implementation. The source population and code paths are visible, but uniform return ownership/cost policy and complete original-layer evidence are not established; changing the core return/inventory path now could create unsupported stock or reverse the wrong cost. The next work should be a separately scoped policy/source-link design and mocked failure/replay tests, followed only after approval by isolated-database validation. No schema need is presumed; determine it after the required source linkage is specified.
