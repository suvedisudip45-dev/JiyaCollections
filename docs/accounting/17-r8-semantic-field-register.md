### Delivered-sale event and posting path

`frontend` checkout calls `POST /api/order/place` (`backend/routes/orderRoute.js` → `orderController.placeOrder`). It creates unpaid COD orders and does **not** post sales revenue merely because an order exists. Supported delivery transitions in `deliveryService.applyNcmStatus` and distributor self-delivery enqueue the stable `DELIVERY_SALE:{orderId}` snapshot; `accountingOutboxService.processDeliveryAccountingOutbox` calls `accountingPostingEngine.postDeliveredOrderAccounting`. That poster calculates Decimal VAT/taxable bases and COGS, posts the sales journal, creates sales invoice and customer/manufacturer documents in the posting transaction, and is protected by the existing journal/outbox idempotency keys.

R22 changed non-COD sales without a source-linked receipt to customer receivables. A `payment=true` assertion without a linked receipt is rejected and permanently blocked in the outbox for review; it is not treated as Bank/Cash evidence. COD delivery remains a carrier/distributor receivable, not company cash. Receipt and correction paths (`recordCustomerReceipt`, `reverseCustomerReceipt`, independent correction approval, and read-only receipt reconciliation) were not changed. The older `postSalesOrderAccounting` helper has no production caller found by the repository search; it was converted to Decimal arithmetic, but its source/payment behavior is not a substitute for the mounted outbox path.

Distributor inventory consumption occurs in the fulfillment service; manufacturer cost recognition uses cost-layer snapshots. R22 tests validate poster journal values with an in-memory client, not atomic persistence between delivery, source inventory movement, journal, and subledger. Cancellation, returns/refunds, COD remittance, and inventory reversals are not complete in this slice. In particular, do not infer cash from `Order.payment` or COD delivery, and do not infer courier remittance from delivery status.

### R22 classifications, limitations, and remaining arithmetic

- In this bounded slice, `Product.price` and `Product.costPrice` are unit-price/unit-cost fields (classification 4); `Order.amount`, `Order.deliveryFee`, and `Order.loyaltyDiscount` are monetary amounts (classification 1). `Product.discount` is a percentage/rate (classification 4), not a money amount. `Order.items` JSON quantity/price members are measurements and monetary snapshots whose historical schema is JSON. These are **not totals for the full R8 register**.
- Checkout and direct-order pricing still use JavaScript Number for product prices, discounts, line totals, shipping, rewards, split allocations, and Float persistence. The nearest-NPR-5 checkout behavior remains unchanged pending its policy evidence. Product/order schema fields were not changed.
- Delivered-sale and legacy sale posting no longer use Number arithmetic for sale amount, VAT, quantity, or COGS. The delivered poster intentionally converts existing Float/JSON source values to strings before Decimal parsing; new strict decimal-string API boundaries and precision recovery require a compatible schema/API migration.
- Selected order history, customer lifetime totals, paper-bill export, discount analytics, and some dashboards still use Number or raw Float sources. `manufacturerSummaryReportingService` has Decimal calculations for its traced direct-order path. No complete source-to-all-report/export/API or all-four-portal trace is claimed.
- Legacy return/refund posting, other COGS/inventory paths, and checkout calculations still need separate implementation and tests. The R22 delivery poster does not validate persisted inventory movement or prove source-to-journal consistency.

- No schema or migration was changed in R21 or R22.

### Commercial rounding and remaining paths

The storefront applies `NEAREST_NPR_5_V1` to the final checkout payable (including applicable shipping, rewards, and adjustments), after first rounding to whole rupees: last digits 0–3 down, 4–7 to 5, and 8–9 up to the next ten. It is not the accounting NPR two-place HALF_EVEN policy. Existing UI documentation and `backend/tests/orderAmount.test.js` establish behavior, not an approved effective-dated commercial policy. R23 records the rule in snapshots and preserves it; no evidence establishes that shipping or discounts should independently use nearest-5 rounding. Direct-order paths retain their existing two-place NPR final quantization rather than being silently normalized to the storefront rule. Separately, percentage product discounts retain the existing positive-price `Math.round` behavior at the **per-unit** boundary (implemented as Decimal HALF_UP to zero fractional digits) before line multiplication; this is also commercial behavior, not NPR accounting quantization.

`toLegacyFloatMirror` necessarily converts a Decimal to Number for writes to current Float columns; this is a compatibility mirror, not exact persistence. Exact v2 JSON amounts and snapshot-aware readers reduce dependence on that mirror, but historic source Float and JSON Number values cannot recover lost digits. Remaining Number-based or incomplete paths include legacy reports/exports and API clients still consuming numeric fields, product mutation/serialization, parts of discount/campaign configuration, and return/refund/exchange and inventory valuation/COGS flows. R18/R19 remain unapplied; no migration was prepared or applied for these fields.

Historical v2 snapshots preserve accepted line prices, quantities, line totals, percentage inputs where supplied, and aggregate order-level discounts, but do not consistently separate original catalog price and each per-line product/location/bundle discount amount. New v3 snapshots capture price steps and source amounts where production writers have that evidence; cart fallback, unclassified adjustments, legacy item readers, and Float source precision can still leave provenance partial. Do not treat the JSON snapshot alone as proof of historic discount details.
